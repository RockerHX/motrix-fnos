## 2. FUTURE-KEY-01：多个有名称的访问密钥

状态：待规划，当前不实施。

### 2.1 目标

将当前“公网/反向代理 Token”和“局域网 Token”两个全局凭据平滑演进为多个可管理的访问密钥。用户可以为不同客户端分别创建密钥，例如“Chrome 扩展”“手机”“公网解析站”，单个客户端泄露或停用时无需轮换其他客户端的凭据。

每个访问密钥至少包含：

- 用户可识别且可修改的名称。
- 明确的入口作用域，例如仅允许公网/反向代理入口、仅允许局域网入口；不得因请求 Header 或来源推断扩大作用域。
- 只用于展示的掩码，不通过普通查询接口返回原文。
- 创建时间和最后使用时间；最后使用时间的更新策略必须避免为每次 RPC 制造高频 SQLite 写入。
- 独立撤销和独立轮换能力，不能影响其他密钥。
- 新建或轮换后的原文只显示一次，关闭弹窗或离开设置页面后立即从前端状态清除。

### 2.2 安全与持久化原则

- 密钥由服务端使用系统随机源生成，强度不得低于当前 32 字节随机 Token。
- 请求鉴权继续只使用内存态和常量时间比较，请求过程不得读取 SQLite，也不得记录密钥原文。
- 持久化方案必须在开发启动前完成安全评审，优先保存不可逆摘要或等价的验证材料；若兼容迁移阶段必须短期读取旧明文 Token，应明确迁移完成条件和清理路径。
- 掩码、名称、作用域、创建时间、最后使用时间和撤销状态可以返回管理端；密钥原文不得通过列表、详情、诊断、日志或导出接口再次返回。
- 最后使用时间应在内存聚合并限频持久化，应用退出时尽力保存；统计失败不得影响合法 JSON-RPC 请求。
- 所有管理写接口继续要求 Web Session、CSRF 和现有管理鉴权；数据库写入失败时不得改变内存中的有效密钥集合。

### 2.3 管理能力与体验

- 提供密钥列表、创建、重命名、轮换和撤销能力，并清楚展示名称、作用域、掩码、创建时间和最后使用时间。
- 创建和轮换必须使用一次性原文弹窗，提供复制操作和无法再次查看的明确提示。
- 撤销与轮换前说明影响范围；轮换只使该密钥旧值失效，撤销只影响该密钥对应客户端。
- 公网与局域网指南、帮助和诊断按作用域展示密钥状态，不显示原文，不把局域网密钥推荐给公网入口。
- 无密钥、全部撤销、迁移中和持久化失败均需有明确状态，前端失败时回滚受控交互状态。

### 2.4 从两个全局 Token 平滑迁移

1. 升级时读取现有公网 Token 与局域网 Token，分别创建带保留名称和对应入口作用域的兼容密钥；已有客户端无需立即修改配置。
2. 迁移后的鉴权统一进入命名密钥验证路径，但公网密钥仍不能用于局域网入口，局域网密钥也不能用于公网/反向代理入口。
3. 旧全局 Token 配置在成功迁移并持久化后标记为已迁移，不得在每次启动重复创建密钥；迁移失败时保持旧凭据继续可用并给出管理端诊断。
4. 用户可逐个创建新密钥并撤销保留的兼容密钥，不设置强制失效日期，不在升级时中断现有 Lucky、浏览器扩展或手机客户端。
5. 回滚到仍使用两个全局 Token 的版本前，必须明确旧版本能否读取迁移后的兼容凭据；不能保证时应保留可恢复的回滚信息并在发布说明中提示。

### 2.5 测试与验收

- 覆盖多密钥创建、命名、作用域隔离、掩码、一次性原文、轮换、撤销和重启恢复。
- 覆盖 HTTP、WebSocket、batch 与 `system.multicall`，确认每个子调用继承入口作用域。
- 覆盖公网/局域网密钥跨入口拒绝、撤销立即失效、数据库关闭后内存校验和敏感信息不入日志。
- 覆盖旧双 Token 首次迁移、重复启动幂等、迁移写入失败、旧客户端兼容和版本回滚。
- 覆盖最后使用时间限频写入和空闲文件稳定性，不能因每次推送任务持续唤醒磁盘。
- 在真实 Lucky 反向代理、RFC1918 局域网客户端和至少一种浏览器扩展或发送工具上完成实机验收。

## 3. FUTURE-NEXT-01：1.9.0 Aria2 Next 升级

状态：未启动。原独立预留计划已完整并入本清单，当前不实施。

基线：1.8.x 稳定后再启动。

版本快照：截至 2026-08-01，本项目使用 Aria2 Next 2.4.9，上游最新稳定版为 2.5.4。正式开发前必须重新确认最新稳定版及其 Release Notes，不能直接假定目标仍是 2.5.4。

### 3.1 目标

1. 将内置 Aria2 Next 从 2.4.9 升级到开发启动时确认的最新稳定版本。
2. 保持 fnOS x86_64 与 ARM64 双架构 FPK 可安装、可启动和可下载。
3. 保持 1.8.x 已建立的生命周期、任务持久化、JSON-RPC 兼容和空闲磁盘低 I/O 约束。
4. 评估并按实际产品价值接入新版 Aria2 Next 能力，不为了追赶功能而直接暴露底层 RPC。
5. 完成自动化验证和至少一台目标 fnOS 设备的实机验收后，才允许发布 1.9.0。

### 3.2 不属于本轮目标的内容

- 不在 1.8.x 修复阶段提前替换 Aria2 Next。
- 不把 RPC 专用监听器改成完整、无约束的 Aria2 RPC 透传服务。
- 不因为上游新增字段而破坏现有 HTTP、JSON-RPC 或前端响应结构。
- 不接入仅适用于 Docker、Android、macOS 或 Windows 的能力，除非它直接影响 Linux FPK 产物。
- 不在没有用户场景和安全边界的情况下增加数据库字段或设置项。

### 3.3 已知上游变化基线

从 2.4.9 到 2.5.4 的主要变化如下；正式开发时需要重新检查目标版本之后新增的所有变化。

| 范围 | 变化 | 对本项目的关注点 |
| --- | --- | --- |
| 2.5.0 | 日志切换到 spdlog，新增日志大小和保留数量限制，轮转文件命名变化 | 日志路径、轮转、清理行为和空闲磁盘写入必须重新验证 |
| 2.5.1 | 新增 BT Peer Blocklist，支持 IPv4、IPv6 和 CIDR | 评估是否需要提供管理能力，默认不直接暴露底层文件路径 |
| 2.5.2 | 增强 BT Peer RPC，修复 MSE 加密兼容，重构构建系统 | 验证 BT、磁链、做种、加密连接和 Linux 运行依赖 |
| 2.5.3 | `aria2.getVersion` 增加产品与 RPC 协议信息，改进 TLS 和 Peer 控制 | RPC 反序列化必须兼容新增字段，外部兼容响应保持稳定 |
| 2.5.4 | 改进 TLS 错误，修复 Android 与 Docker 行为 | Linux FPK 重点验证 TLS 错误信息，忽略无关平台功能 |

### 3.4 实施任务

#### NEXT-01：确认目标版本和供应链

- 重新检查 Aria2 Next 最新稳定版、发布日期、Release Notes、tag 和完整代码比较。
- 检查许可证、发布资产、双架构 checksum 和上游构建来源。
- 确认 Linux x86_64、Linux ARM64 二进制的动态链接依赖、最低 glibc 要求和 fnOS 内核兼容性。
- 记录目标版本、下载 URL、SHA-256、文件大小和二进制架构。
- 若最新版本发布不足两周或存在明显回归反馈，可选择经过验证的次新稳定版，但必须在计划中记录原因。

完成标准：目标版本和双架构资产均可验证，且不存在已知的 fnOS 运行阻断问题。

#### NEXT-02：升级双架构 Sidecar

- 更新 `scripts/fetch-aria2-next.mjs` 中的固定版本。
- 下载并校验新的 checksum 文件、x86_64 和 ARM64 二进制。
- 确认 `scripts/stage-aria2-sidecar.mjs` 和 FPK stage 仍将正确架构放入 `app/bin/aria2-next`。
- 更新 SBOM、依赖说明和打包文档中的版本证据。
- 不保留无法解释的旧二进制、旧 checksum 或混合架构产物。

完成标准：双架构 FPK 解包后都只包含对应架构且校验通过的 Aria2 Next。

#### NEXT-03：适配启动参数、日志和运行态

- 审查现有启动参数在目标版本中的名称、默认值和语义。
- 验证 `--console-log-level=warn`、session、DHT、RPC、CA 证书和日志路径参数。
- 评估接入 `--log-max-size`、`--log-max-files`，为 Aria2 日志设置明确的有界保留策略。
- 适配新的 spdlog 轮转文件命名和旧日志历史清理行为。
- 确保 PID、进程命令行归属判断、RPC secret 和运行态记录仍能识别新版 sidecar。
- 升级安装不得误删用户下载文件、SQLite、session 或仍有价值的诊断日志。

完成标准：启动、停止、崩溃恢复和升级安装行为与现有生命周期契约一致。

#### NEXT-04：适配内部 RPC 与外部兼容层

- 使用真实目标版本验证内部依赖的方法：
  - `aria2.getVersion`
  - `aria2.addUri` / `aria2.addTorrent`
  - `aria2.tellStatus` / `aria2.tellActive` / `aria2.tellWaiting` / `aria2.tellStopped`
  - `aria2.pause` / `aria2.unpause` / `aria2.remove`
  - `aria2.changeGlobalOption`
  - `aria2.saveSession`
- 兼容 `aria2.getVersion` 新增的产品身份和 RPC contract 字段，未知字段不得导致解析失败。
- 外部 `/jsonrpc` 继续只提供经过审查的兼容方法，不直接透传任意方法。
- 保持现有 `aria2.getVersion`、`aria2.getGlobalOption`、`aria2.addUri` 和 `system.multicall` 响应兼容。
- 新版 RPC 错误需要映射为清晰的中文错误，但不得记录 Token、RPC secret 或敏感 URL query。

完成标准：现有外部发送工具不需要改配置即可继续查询和推送任务。

#### NEXT-05：评估新版功能

以下功能必须先确认用户场景，再决定是否进入 1.9.0：

1. BT Peer Blocklist
   - 评估本地规则文件、IPv4/IPv6/CIDR 和运行时更新。
   - 如果接入，应由 Rust 服务校验和管理规则，不允许前端传入任意系统文件路径。
   - 更新失败时保留上一份有效规则，并提供明确诊断信息。

2. BT Peer 详情
   - 评估是否在诊断页面展示客户端、进度、传输量和连接状态。
   - 默认不做高频轮询，避免为了展示 Peer 信息持续唤醒 Aria2 或制造磁盘/网络负担。

3. 私有种子状态
   - 评估是否用于改善做种状态判定和用户提示。
   - 不改变私有种子的安全语义，不向无关接口暴露敏感 Tracker 或 Peer 数据。

4. TLS 错误详情
   - 将证书验证失败、CA 缺失和普通网络失败区分为可理解的错误信息。
   - 继续优先使用 fnOS 系统 CA，不打包来源不明的证书集合。

完成标准：只实现有明确用户价值、能够安全验收且不会破坏空闲策略的功能。

- 使用真实 Aria2 Next 二进制覆盖启动、RPC ready、版本读取、session 保存和停止。

- 重跑生命周期竞态、停止许可、失败退避和空闲文件稳定性测试。
- 确认只读 API、重复 `cmd/status` 和已停止状态的 JSON-RPC 查询不启动 Aria2、不写 SQLite 或日志。

#### NEXT-07：fnOS 实机验收

- 分别安装 ARM64 和 x86_64 FPK；若暂时只有一种设备，另一架构至少完成解包和依赖检查，并在发布前补齐实机结果。
- 验证应用启动、停止、重启、卸载重装和保留数据升级。
- 验证普通 HTTP/HTTPS 下载、磁链、种子、暂停恢复、做种和外部 JSON-RPC 推送。
- 验证 HTTPS 证书正常、证书错误提示明确、系统 CA 路径有效。
- 验证 Aria2 日志轮转文件、数量、大小和升级前旧日志处理符合预期。
- 在无任务、暂停任务、完成任务、错误任务和确认等待状态下检查 Aria2 自动停止。
- 重新收集 Motrix 文件事件、进程 I/O、块设备 I/O 和 fnOS 硬盘休眠证据。
- 没有块设备与 fnOS 实机证据时，不得宣称新版已经实现物理硬盘休眠。

完成标准：至少一台目标 fnOS 设备通过完整验收，另一架构不存在发布阻断项。

### 3.5 兼容性原则

- SQLite schema 只有在新功能确实需要长期状态时才允许修改，并必须提供迁移与回滚方案。
- 现有任务、session、种子 metadata 和用户下载文件必须能从 1.8.x 平滑恢复。
- HTTP 和 JSON-RPC 的既有响应字段保持兼容；新增字段只能是可选扩展。
- 外部 JSON-RPC Token、Web 管理密码和 Aria2 内部 RPC secret 继续保持三者职责隔离。
- 新功能不得绕过 Aria2 生命周期协调器，也不得因只读查询启动已经停止的引擎。
- 任何新增后台轮询都必须说明频率、停止条件和对磁盘休眠的影响。

### 3.6 发布与回滚

- 1.9.0 发布包必须同时记录 Motrix 版本、Aria2 Next 版本、架构和 SHA-256。
- 保留上一版 1.8.x FPK、旧 Aria2 Next 2.4.9 资产和回滚说明，直到 1.9.0 实机稳定。
- 若新版无法读取旧 session，应优先保护 SQLite 任务和用户文件，不得自动清空数据重新开始。
- 若发现空闲磁盘 I/O、BT 恢复、HTTPS 或双架构兼容回归，应停止发布并回退 sidecar，不在用户设备上试错。
