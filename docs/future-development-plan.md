## 2. FUTURE-KEY-01：多个有名称的访问密钥

状态：待规划，当前不实施。

### 2.1 目标

将当前“公网/反向代理 Token”和“局域网 Token”两个全局凭据平滑演进为多个可管理的访问密钥。用户可以为不同客户端分别创建密钥，例如“Chrome 扩展”“手机”“公网解析站”，单个客户端泄露或停用时无需轮换其他客户端的凭据。

每个访问密钥至少包含：

- 用户可识别且可修改的名称。
- 明确的入口作用域，例如仅允许公网/反向代理入口、仅允许局域网入口；不得因请求 Header 或来源推断扩大作用域。
- 只用于展示的掩码，不通过普通查询接口返回原文。
- 创建时间和最后使用时间；最后使用时间的更新策略必须避免为每次 RPC 制造高频 SQLite 写入。
- 独立撤销和独立轮换能力，不能影响其他密钥。
- 新建或轮换后的原文只显示一次，关闭弹窗或离开设置页面后立即从前端状态清除。

### 2.2 安全与持久化原则

- 密钥由服务端使用系统随机源生成，强度不得低于当前 32 字节随机 Token。
- 请求鉴权继续只使用内存态和常量时间比较，请求过程不得读取 SQLite，也不得记录密钥原文。
- 持久化方案必须在开发启动前完成安全评审，优先保存不可逆摘要或等价的验证材料；若兼容迁移阶段必须短期读取旧明文 Token，应明确迁移完成条件和清理路径。
- 掩码、名称、作用域、创建时间、最后使用时间和撤销状态可以返回管理端；密钥原文不得通过列表、详情、诊断、日志或导出接口再次返回。
- 最后使用时间应在内存聚合并限频持久化，应用退出时尽力保存；统计失败不得影响合法 JSON-RPC 请求。
- 所有管理写接口继续遵循现有管理鉴权：保护开启时要求有效管理员 JWT，保护关闭时允许匿名管理；数据库写入失败时不得改变内存中的有效密钥集合。

### 2.3 管理能力与体验

- 提供密钥列表、创建、重命名、轮换和撤销能力，并清楚展示名称、作用域、掩码、创建时间和最后使用时间。
- 创建和轮换必须使用一次性原文弹窗，提供复制操作和无法再次查看的明确提示。
- 撤销与轮换前说明影响范围；轮换只使该密钥旧值失效，撤销只影响该密钥对应客户端。
- 公网与局域网指南、帮助和诊断按作用域展示密钥状态，不显示原文，不把局域网密钥推荐给公网入口。
- 无密钥、全部撤销、迁移中和持久化失败均需有明确状态，前端失败时回滚受控交互状态。

### 2.4 从两个全局 Token 平滑迁移

1. 升级时读取现有公网 Token 与局域网 Token，分别创建带保留名称和对应入口作用域的兼容密钥；已有客户端无需立即修改配置。
2. 迁移后的鉴权统一进入命名密钥验证路径，但公网密钥仍不能用于局域网入口，局域网密钥也不能用于公网/反向代理入口。
3. 旧全局 Token 配置在成功迁移并持久化后标记为已迁移，不得在每次启动重复创建密钥；迁移失败时保持旧凭据继续可用并给出管理端诊断。
4. 用户可逐个创建新密钥并撤销保留的兼容密钥，不设置强制失效日期，不在升级时中断现有 Lucky、浏览器扩展或手机客户端。
5. 回滚到仍使用两个全局 Token 的版本前，必须明确旧版本能否读取迁移后的兼容凭据；不能保证时应保留可恢复的回滚信息并在发布说明中提示。

### 2.5 测试与验收

- 覆盖多密钥创建、命名、作用域隔离、掩码、一次性原文、轮换、撤销和重启恢复。
- 覆盖 HTTP、WebSocket、batch 与 `system.multicall`，确认每个子调用继承入口作用域。
- 覆盖公网/局域网密钥跨入口拒绝、撤销立即失效、数据库关闭后内存校验和敏感信息不入日志。
- 覆盖旧双 Token 首次迁移、重复启动幂等、迁移写入失败、旧客户端兼容和版本回滚。
- 覆盖最后使用时间限频写入和空闲文件稳定性，不能因每次推送任务持续唤醒磁盘。
- 在真实 Lucky 反向代理、RFC1918 局域网客户端和至少一种浏览器扩展或发送工具上完成实机验收。

## 3. FUTURE-REFACTOR-01：设置服务分层重构

状态：待规划，当前不实施。

### 3.1 背景

当前 `server/src/api/settings.rs::update_settings` 除了解析 HTTP 请求，还负责保存 `AppConfig`、刷新内存中的默认下载目录、记录日志，并在 Aria2 可用时即时应用全局下载配置。功能行为正确，但业务编排位于 `api/`，与架构文档规定的 `api -> service -> domain -> persistence` 分层不一致。

### 3.2 重构范围

- 将设置保存、运行时状态刷新和 Aria2 全局配置应用的编排移入 `server/src/settings/service.rs` 或同职责的 settings service 模块。
- `api/settings.rs` 只保留路由、请求解析、响应转换和错误映射。
- 不建立脱离 settings 领域的通用业务层。

### 3.3 必须保持的行为

- SQLite 配置持久化成功后，Aria2 即时应用失败不得回滚已保存配置。
- Aria2 未运行或生命周期正在转换时，配置仍然保存，并记录“下次启动生效”的诊断信息。
- 设置保存不得为了即时应用而主动启动 Aria2，也不得绕过生命周期协调器。
- 现有 HTTP 响应、错误状态和前端交互保持兼容。

### 3.4 测试与启动门禁

- 补充 settings service 对保存顺序、生命周期转换、Aria2 不可用和即时应用失败的测试。
- API 测试只覆盖请求/响应转换和错误映射，不重复测试 service 内部编排。
- 启动前先完成架构边界评审，确认不改变现有持久化和运行时失败语义。

## 4. FUTURE-TASKS-01：回收站两阶段任务与文件删除

状态：待规划，当前不实施。

### 4.1 目标

将“移除下载任务”和“不可恢复地删除用户文件”拆为两个阶段：普通列表删除只移除 Aria2 任务并放入回收站，用户文件保留；只有在回收站永久删除时，用户才可明确选择是否同时删除该任务的下载文件。

### 4.2 产品与接口语义

- 普通任务列表的“删除”不再提供删除文件选项，成功后任务进入回收站，保留文件用于恢复和续传。
- 回收站单任务“永久删除”提供“同时删除下载文件”复选框，默认不勾选，并明确标注已勾选时不可恢复。
- “清空回收站”使用相同的文件删除选择；批量操作逐任务执行，部分失败不回滚已经完成的任务。
- 未勾选删除文件时，永久删除只移除任务记录和应用私有恢复 metadata，用户下载文件保持不变。
- 当前 `DELETE /api/tasks/:id?deleteFiles=true|false` 已是公开契约。实施前必须确定兼容策略：保留旧调用的既有语义并标记废弃，或作为明确的不兼容变更迁移到永久删除请求；不得静默改变旧调用的文件删除结果。

### 4.3 数据安全与异步清理

- 勾选删除文件的永久删除必须复用既有任务专属路径校验、原子暂存、持久化操作记录和有界后台清理，禁止直接递归删除授权目录根。
- 文件清理未完成、失败或服务重启时，回收站记录必须保留为可诊断、可重试状态；不得在文件仍待清理时先静默丢弃任务记录。
- 清理进行中时恢复、重复永久删除和其他会改变同一文件集的操作必须返回明确冲突。
- 已按旧语义进入回收站且 `filesDeleted=true` 的历史任务不得重复删除文件；升级后永久删除只清理其记录和私有 metadata。

### 4.4 测试与启动门禁

- 覆盖单任务删除、恢复、永久删除（保留文件和删除文件）、清空回收站、部分失败、文件暂存失败、后台清理失败和重启对账。
- 覆盖 URL、种子、磁链、已完成和无文件任务，确认只能清理应用可证明归属的文件。
- 覆盖旧 HTTP 调用兼容或明确的迁移/拒绝响应，不能让既有调用方在无感知情况下丢失或保留错误的文件。
- 启动前先同步更新 `docs/architecture.md`、`docs/api-contract.md` 和 UI 产品需求，再将事项状态更新为进行中。

## 5. FUTURE-GATEWAY-01：统一网关可信性验证

状态：延期、非阻塞，不属于当前功能修复。当前 Motrix 继续使用已经实机验证的端口入口；本实验不得阻塞功能开发、常规修复或正式发布。

实验必须使用独立 appname 的最小 FPK，不得直接修改 Motrix 主包。最小包只包含：

- 一个 `gatewayPrefix` 与一个位于 `TRIM_APPDEST` 的 Unix Socket。
- 一个返回固定 HTML 的根路由和一个返回固定 JSON 的健康检查路由。
- 一个 SSE 或 WebSocket 回显路由，用于验证长连接转发。
- 记录请求 path、`X-Trim-Userid`、`X-Trim-Isadmin` 和 `X-Trim-Username` 是否存在的脱敏日志。

实机验证矩阵：

1. 全新安装后，确认 `trim_sac/open_gateway` 生成入口和转发表，登录用户访问公开路径返回 `200`。
2. 直接请求 Unix Socket 与通过 fnOS nginx 请求得到一致响应，并记录网关转发时 path 是保留还是剥离前缀。
3. 未登录请求被 fnOS 拒绝；已登录请求携带可信 `X-Trim-*` Header。
4. 根 HTML、子路径、静态资源、健康检查及 SSE/WebSocket 均能通过同一网关前缀访问。
5. 分别验证停止后启动、覆盖升级、卸载重装和设备重启，确认 Socket 清理与路由注册不会残留或丢失。
6. 收集 fnOS 版本、入口数据库记录、nginx access/error log、注册服务日志和最小 FPK 校验和，形成可复现报告。

迁移门禁：

- 最小 FPK 在目标 fnOS 实机上完整通过上述矩阵后，才能提出 Motrix 统一网关迁移方案。
- 迁移前必须先更新 `docs/architecture.md`、`docs/api-contract.md` 和 `docs/fpk-packaging.md`，并明确端口模式回退方案。
- Motrix 的候选实现必须单独验证 FPK 最终产物和真实 fnOS 转发链路；仅有 Axum Router 测试或 Unix Socket 直连测试不算通过。
- 任一注册、鉴权、路径或长连接场景失败时，Motrix 继续保持当前端口入口，不合并实验代码。
