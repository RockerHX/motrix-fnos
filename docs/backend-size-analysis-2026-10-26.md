# Rust 后端体积分析与编译优化（2026-10-26）

## 1. 结论与变更边界

本次从 `feature/2.0.1` 的 `405099817a55c73a279cb74773b2e6babc1da7f7` 开始，初始工作区干净。此前四阶段的源码清理与性能优化见 [全仓审计报告](codebase-audit-2026-10-25.md)，本报告的收益单独计算。

最终仅在 [server/Cargo.toml](../server/Cargo.toml) 的发布配置增加两行：

```toml
[profile.release]
strip = true
lto = "fat"
codegen-units = 1
```

保留默认速度优化等级 `3`、异常展开、安全校验、依赖及运行接口；开发和普通测试配置沿用原值。本次业务代码、测试代码增删均为零，发布配置新增两行，并新增本报告。版本保持 `2.0.0`；不推送、不发布、不操作真实 NAS。

最终收益如下，大小单位均为字节：

| 架构 | 后端：优化前 → 优化后 | 后端减少 | FPK：优化前 → 优化后 | FPK 减少 |
| --- | ---: | ---: | ---: | ---: |
| ARM64 | 14,703,336 → 10,292,992 | 4,410,344（30.00%） | 16,130,362 → 14,574,399 | 1,555,963（9.65%） |
| x86_64 | 16,383,840 → 11,626,912 | 4,756,928（29.03%） | 16,059,165 → 14,457,759 | 1,601,406（9.97%） |

解包逐文件比对确认：应用内容仅 `bin/motrix-fnos-server` 改变，外层 manifest 仅自动生成的 `checksum` 改变；前端、引擎、生命周期脚本及其他文件内容一致。FPK 差值来自实际产物，不按原始组件占比分摊压缩收益。

## 2. 原始包体组成

单位为字节，MB 按十进制换算。下表为基线 FPK 解包后的文件大小，不能相加当成压缩 FPK 大小。

| 组件 | ARM64 | x86_64 |
| --- | ---: | ---: |
| Rust 后端 | 14,703,336 | 16,383,840 |
| Aria2 Next 2.8.6 | 18,317,056 | 19,252,656 |
| Web UI（`ui/dist/`） | 1,274,219 | 1,274,219 |
| 压缩 FPK | 16,130,362 | 16,059,165 |

前端确实很小；引擎是最大的单个组件，约占上述三个解包主体合计的 52%–53%，后端约占 43%–44%。因此后端也有值得优化的空间。优化 Rust 后端不会缩小 Aria2，自然也不能把后端缩小比例直接当作整个 FPK 的缩小比例。

优化后引擎占上述三个解包主体合计约 60%–61%，成为更主要的剩余体积来源。

基线两个 ELF 均已无 `.debug*` 和 `.symtab`。已有 `strip = true` 生效，重复剥离调试信息没有这次所需的收益。x86 正式 ELF 主要段的变化如下：

| 段 | 基线字节 | 优化后字节 | 含义 |
| --- | ---: | ---: | --- |
| `.text` | 11,948,897 | 8,816,193 | 业务、运行时及依赖的机器码 |
| `.rodata` | 1,244,340 | 1,051,308 | 常量、字符串等只读数据 |
| `.eh_frame` | 1,251,256 | 657,800 | 异常展开信息 |
| `.gcc_except_table` | 775,416 | 364,824 | 异常处理表 |
| `.eh_frame_hdr` | 178,004 | 90,772 | 展开信息索引 |
| `.rela.dyn` | 567,816 | 364,800 | 动态重定位 |
| `.data.rel.ro` | 355,176 | 242,128 | 重定位后只读数据 |

这些异常处理段属于运行语义，不能当作残留调试信息删除。此次通过优化机器码及相关表项减少体积，保留异常展开。

## 3. 符号和依赖分析

使用匹配 Rust 1.97.1 的 LLVM 工具，对额外保留符号的 x86 诊断构建分析。按函数地址去重后，基线函数符号的部分命名空间分组如下：

| 命名空间或分组 | 函数符号大小合计（字节） |
| --- | ---: |
| `motrix_fnos_server` | 2,685,541 |
| `core` | 2,116,570 |
| 其他 C / 匿名符号 | 1,452,218 |
| `sqlite3*` 命名 C 函数 | 580,017 |
| `alloc` | 447,136 |
| `tokio` | 435,600 |
| `rustls` | 337,678 |
| `axum` | 293,334 |
| `std` | 227,577 |
| `sqlx_core` | 220,728 |
| `serde_json` | 208,839 |

**这不是各依赖的精确占比或可删除大小。** 泛型实例、内联、别名和 C 内部函数会影响归属；例如 `core` 分组也可能承载业务类型的泛型实现，`sqlite3*` 不涵盖全部 SQLite。数据和展开表不在该函数符号统计中。

诊断基线中，`ensure_aria2_ready_locked::{closure#0}` 的相同显示名称对应 7 个不同地址，合计 343,554 字节；ThinLTO + 单代码生成单元的诊断构建中为 2 个地址、95,115 字节。这说明异步与泛型代码的生成方式会影响体积，相同显示名称也不代表可以删除的业务副本。

保留符号会改变构建结果：诊断基线和 ThinLTO 诊断构建的 `.text` 分别比对应正式剥离版本大 27,232 / 448 字节。符号分析仅用来解释来源，正式收益以实际交付 ELF 和 FPK 为准。原始配置的 x86 正式重建与归档基线逐字节一致，SHA-256 为 `6043a4078ef93f38518f3243ebae9fdc68dc65e80f39c0e9c53754daf384a79f`。

Cargo feature 树确认 TLS 使用 `ring 0.17.14`，没有 `aws-lc-rs`，未发现此前可能担心的双 TLS 密码实现并存证据。依赖树条目、宏依赖和源码行数不等于最终链接占用。本次不更换 JWT、TLS、SQLite 等实现，也不新增项目依赖。

## 4. 编译参数对照与选择

固定业务源码、锁文件、Rust 1.97.1、Linux glibc baseline 2.36 和现有交叉构建脚本。候选先通过 `CARGO_PROFILE_RELEASE_*` 环境变量试验，构建后立即复制二进制到独立目录，避免覆盖。所有候选均剥离符号、保留异常展开。

表中 `false` 沿用 Cargo 默认发布语义，仍可能进行 crate 内部的本地 ThinLTO；`fat` 增加跨 crate 的完整链接优化。

| 候选 | 优化等级 | LTO | 代码生成单元 | ARM64 ELF 字节 | x86 ELF 字节 | 判断 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| 基线 | 3 | false | 默认 16 | 14,703,336 | 16,383,840 | 对照 |
| `thin1` | 3 | thin | 1 | 10,950,896 | 12,323,472 | 快照序列化有稳定回退，未采用 |
| `thin1-s` | s | thin | 1 | 8,838,680 | 9,781,472 | 密码校验明显变慢，未采用 |
| `thin1-z` | z | thin | 1 | 8,328,056 | 9,535,120 | 密码校验和序列化明显变慢，未采用 |
| `thin16` | 3 | thin | 16 | 15,043,544 | 16,636,928 | 两架构均增大，未采用 |
| `cgu1` | 3 | false | 1 | 未构建 | 未构建 | 仅追加宿主性能对照 |
| `fat1` | 3 | fat | 1 | 10,292,992 | 11,626,912 | 已采用，标准打包实测 |

第一组宿主对照中，`thin1` 大快照序列化中位数为 7.031 ms，基线为 6.444 ms，约慢 9.1%，三轮结果一致。`s/z` 的密码校验约从 16 ms 增至 20.4 ms，慢约 28%；`z` 的大快照序列化从 6.444 ms 增至 18.508 ms。不能只按最小二进制选择这些参数。

追加完整 LTO 与仅单代码生成单元的交错对照后，完整 LTO 在本机所测路径的中位数持平或略低，选为最终候选。不同批次分别保留自己的基线，不跨批次拼接性能收益。`cgu1` 没有 Linux 体积测量，不估计其节省量。

## 5. 宿主发布模式性能测量

环境为 Apple M1、16 GiB 内存、macOS 15.7.5。外部驱动链接当前真实业务库，采用相同磁盘 SQLite WAL/NORMAL、可控回环 RPC、具有就绪握手及正常 SIGINT 退出的所属替身子进程，不执行下载。构建全部完成后再采样，各轮交错候选顺序，试跑不计入结果。

场景为：一个活动 BT 任务（100 个文件）；同一活动任务加 300 个历史 BT 任务（每个 100 文件，完成、暂停、回收站各 100 个）。真实 `monitor_tasks_once` 每场景预热 2 轮，测 10 轮、重复 3 次，没有写入计数触发器。另测公开任务 DTO 转换与 JSON 序列化、真实 Argon2id 密码校验、包含数据库读取的 JWT 校验；各预热 3 次，分别测 30 / 30 / 100 次，重复 3 轮。

## 7. 证据、复现与限制

专用归档：`/Users/rockerhx/Desktop/GitHub/motrix-fnos-artifacts/backend-size-2026-10-26/`。这些工具和材料仅服务本项目，放在仓库外，不进入提交或 FPK。

- `compare-*.py`、候选目录：Linux 参数对照的命令、日志、二进制及 SHA-256。
- `build-symbols.py`、`analyze-symbols.py`、`*-symbols/`：诊断符号与分组数据。
- `analyze-elf.py`、`elf-analysis.json`、`elf-hardening.json`：实际 ELF 段、哈希和程序头核对。
- `profile-bench/`、`measure-*.py`、`performance/`：驱动、锁文件、三批交错测量及逐轮 SQLite/JSON；最终选择依据为 `paired3-summary.json`。
- `final/`、`artifact-comparison.json`、验证日志：最终产物、逐文件对照及结果。

例如可用原始配置环境覆盖，在当前源码上复现基线的单架构构建，再及时复制固定输出路径的 ELF：

  CARGO_PROFILE_RELEASE_LTO=false CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16 \

本次没有 Linux 执行环境，未验证 fnOS 实机、长期负载、真实吞吐、全路径性能、内存常驻量和冷启动耗时；交叉编译及解包通过不能代替这些结果。未做干净构建时间或编译峰值内存的对照，缓存构建耗时不用于量化收益；完整 LTO 的发布构建资源成本需在实际 CI 持续观察。

更小的 `s/z` 已有性能代价证据。本次不采用 `panic=abort`、删除异常展开表、可执行文件压缩或替换安全依赖来追求更小数字；后续如需继续缩小，应先测具体依赖及最终场景，再评估兼容代价。
