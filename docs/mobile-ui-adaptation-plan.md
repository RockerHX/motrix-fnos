# 手机端 UI 适配任务计划

> 更新时间：2026-07-05  
> 适用范围：飞牛 fnOS Web UI、飞牛提供的公网子域名入口、飞牛 App 内 WebView/手机浏览器。  
> 长期架构边界仍以 `docs/architecture.md` 为准：本任务只调整 Vue Web UI，不改变 FPK manifest、服务脚本、Rust server、Aria2 sidecar 或 HTTP/SSE 数据流。

## 1. 背景与当前判断

当前基础功能已稳定，桌面浏览器、飞牛 OS 大屏网页和飞牛子域名访问都能正常使用。手机端截图中出现的问题主要是：页面仍按桌面两栏布局渲染，左侧 220px 侧栏占据了手机屏幕大部分宽度，右侧主内容被挤出可视区域；任务空态、按钮、浮动添加按钮和顶部工具栏也没有按窄屏重排。

代码阅读结论：

- `index.html` 已有标准 `viewport`，问题不是缺少基础 viewport 配置。
- `src/layouts/AppShell.vue` 使用固定两栏网格：`220px minmax(0, 1fr)`，并且外层 `height: 100vh; overflow: hidden;`，手机端没有纵向自然滚动空间。
- `src/layouts/SidebarNav.vue` 是桌面侧栏，品牌区、分类、设置和帮助都纵向铺开，手机端没有抽屉、底部导航或紧凑模式。
- `src/features/tasks/components/TaskTable.vue` 使用 Naive UI `NDataTable`，默认列宽合计约 1340px，适合桌面横向表格，不适合手机阅读和操作。
- `src/features/tasks/components/TaskEmptyState.vue`、`src/features/extensions/components/ExtensionsPlaceholder.vue` 的居中卡片/空态适合大屏，窄屏需要压缩图形、改为可滚动内容。
- `TaskCreateDialog`、`SettingsDialog`、`HelpDialog`、`DiagnosticsDialog`、`DebugLogDialog`、`EngineStatusPanel` 等弹窗当前多为 `calc(100vw - 48px)` 宽度或多列布局，手机端需要全屏/近全屏、单列表单、可滚动主体和固定操作区。

因此本任务目标不是“缩放整页”，而是为手机端建立独立的响应式布局策略：桌面保持现状，窄屏切换到单列主内容、紧凑导航、卡片式任务列表和移动端弹窗。

## 2. 目标与非目标

### 2.1 目标

- 手机竖屏宽度 360px 及以上可完整使用核心功能：查看分类、创建任务、查看任务、暂停/继续/删除、打开设置、帮助和诊断。
- 手机横屏、平板和桌面保持可用；桌面现有视觉和操作习惯不回退。
- 飞牛 App WebView 中不再出现“左侧栏占半屏、主内容被截断”的问题。
- 移动端点击目标不小于 44px，底部区域避开 iOS/Android 安全区。
- 不引入新的后端接口，不改变下载业务逻辑。

### 2.2 非目标

- 不实现原生 App UI。
- 不改 FPK 网络穿透、端口入口、manifest、`cmd/*` 生命周期。
- 不重做主题系统，不替换 Naive UI。
- 不在本任务中实现插件、批量下载、BT/磁力等未完成业务能力。

## 3. 响应式设计约定

建议断点：

| 断点 | 范围 | 布局策略 |
| --- | --- | --- |
| mobile | `max-width: 767px` | 单列布局、底部/抽屉导航、任务卡片、全屏弹窗 |
| tablet | `768px - 1023px` | 压缩侧栏或抽屉，任务表格可保留横向滚动 |
| desktop | `min-width: 1024px` | 保持当前两栏桌面布局 |

CSS 约定：

- 优先使用 CSS media query 完成纯布局切换；需要组件分支时再增加轻量 composable。
- 使用 `100dvh` 优先适配手机浏览器地址栏变化，保留 `100vh` fallback。
- 统一处理 `env(safe-area-inset-top/right/bottom/left)`。
- 桌面样式作为默认样式，移动端通过 `@media (max-width: 767px)` 覆盖，降低回归风险。

## 4. 实现策略

本次适配采用 **一套源码、一套业务状态和 API，布局层响应式，复杂展示组件按桌面/移动拆分** 的策略。

约束：

- 不新增独立 App UI 工程，不维护两套前端源码。
- 不新增移动端专用 Pinia store、service、API 或 SSE 数据流。
- `views/` 继续只负责页面编排，不把移动端分支逻辑堆到 `MainWindow.vue`。
- `layouts/` 负责桌面/移动外壳切换，例如桌面侧栏、移动底部导航或移动抽屉。
- `features/*` 内按业务领域拆分展示组件：信息结构差异明显时可以新增移动端展示组件，例如 `TaskMobileList.vue`；业务操作仍复用现有 store/service。
- 只是尺寸、间距、排列变化的组件优先用 CSS media query 适配，例如设置、帮助、诊断和创建任务弹窗。

判断规则：

| 场景 | 推荐做法 |
| --- | --- |
| 只是尺寸、间距、排列变化 | 同一组件 + CSS media query |
| 信息结构明显不同 | 拆桌面/移动展示组件，共享 props、store 和 service |
| 业务逻辑不同 | 先重新审视设计，避免移动端产生独立业务逻辑 |
| 入口、数据流、能力边界都不同 | 才考虑独立路由或独立工程；本任务不采用 |

## 5. 任务拆解

### M0：建立移动端适配基线

范围：`src/App.vue`、全局 CSS、必要时新增 `src/styles/`。

小任务：

- [x] M0.1 定义断点、触控尺寸、顶部/底部安全区等 CSS 变量。
- [x] M0.2 将 `html/body/#app` 的高度策略改为兼容 `100dvh`，避免手机地址栏变化导致内容截断。
- [x] M0.3 保持桌面 `overflow: hidden` 行为，同时为移动端明确哪些容器负责滚动。
- [x] M0.4 建立最小手动测试矩阵：iPhone 390×844、Android 360×800、手机横屏、桌面 1440px。

验收：手机端页面不再因根容器高度策略导致底部按钮不可达。

最小手动测试矩阵：

| 场景 | 视口 | 重点验证 |
| --- | --- | --- |
| iPhone 竖屏 | `390 × 844` | 地址栏伸缩后首屏高度、底部安全区、按钮是否可达 |
| Android 竖屏 | `360 × 800` | 最小主流窄屏宽度下是否出现横向溢出 |
| 手机横屏 | `844 × 390` 或近似尺寸 | 横屏下内容是否被裁切、是否能正常滚动 |
| 桌面浏览器 | `1440 × 900` 或更宽 | 现有桌面 `overflow: hidden` 和全屏布局不回退 |

## 6. 推荐实施顺序

1. 先做 M0 + M1，解决“手机端主内容被侧栏挤没”的核心问题。
2. 再做 M3，让无任务默认页面先可用；这是当前截图里最明显的首屏问题。
3. 做 M4，确保核心“添加任务”流程可用。
4. 做 M2，有任务后将任务列表从桌面表格切换为手机卡片。
5. 做 M5，补齐设置、帮助、诊断、日志等辅助能力。
6. 最后做 M6 + M7 回归和打磨。

## 8. 风险与注意事项

- Naive UI `NDataTable` 不适合作为手机端主展示，不建议只依赖横向滚动；卡片列表更符合手机操作。
- 飞牛 App WebView 可能有自带顶部栏和底部安全区，移动端布局必须预留 `safe-area`。
- `100vh` 在手机浏览器中可能受地址栏影响，优先使用 `100dvh`。
- 不要把业务状态复制成移动端专用 store；移动端和桌面端应共享现有 Pinia store、service 和 HTTP/SSE 数据流。
- 若后续发现飞牛 App WebView 有特殊注入样式或 viewport 行为，应单独记录实机现象，再决定是否需要平台侧文档或实机验证补充。
